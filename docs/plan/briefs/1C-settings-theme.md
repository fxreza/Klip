## 1. Settings: one source of truth
- Make `SettingsManager` a `@MainActor final class SettingsManager: ObservableObject` with `@Published` properties for every setting; setting a property writes UserDefaults immediately (`didSet`) and posts the notifications the app relies on (`.bufferHotkeyChanged`, `.bufferHistoryLimitChanged`, `.bufferStatusBarVisibilityChanged`) exactly when the corresponding value changes. Keep every existing UserDefaults key and value format (`hotkeyModifiers [String]`, `hotkeyKeyCode Int`, `historyLimit Int`, `includePrereleases`, `hideStatusBar`), keep `keyCodeNames`, `HotkeyModifiers`, launch-at-login via `SMAppService`.
- **Do not touch the `HistoryLimit` enum or the `historyLimit` load/save lines** - another agent is replacing them concurrently with this exact API: `enum HistoryLimit: Int, CaseIterable { case k1 = 1000, k5 = 5000, k10 = 10000, unlimited = 0 }` with `static let default`, `maxItems: Int?`, `isUnlimited`, `label`, `subtitle`, `static func from(storedRaw: Int?)`. Write the settings UI against that API (picker over `HistoryLimit.allCases` showing `label` + `subtitle`; keep the existing downgrade warning alert when the new limit is smaller than the current item count). If your worktree still has the old enum, add a temporary shim extension in `Views/SettingsView.swift` behind `// TEMP-SHIM remove at integration` so you can build.
- Delete `SettingsViewModel` from `Views/SettingsView.swift`; the view observes `SettingsManager.shared` directly (`@ObservedObject`). Remove the `save()` button flow if it only existed to push the VM into the manager; settings now apply immediately (that is how macOS settings behave and how the user sees it - note it in your report as a UX change that loses nothing).
- New settings (with UserDefaults keys and defaults): `listFontScale: Double = 1.0` (`fontScale.list`, range 0.8...1.6), `previewFontScale: Double = 1.0` (`fontScale.preview`), `accentTheme: AccentTheme = .system` (`appearance.accent`), `colorScheme: AppColorScheme = .system` (`appearance.colorScheme`), `showPreviewPane: Bool = true` (`appearance.showPreview`), `sidebarCollapsed: Bool = false`, `sidebarWidth: Double = 180`, `previewWidth: Double = 300`, `windowWidth/windowHeight: Double?`. (Phase 2 consumes these.)

## 2. Design tokens (new folder `Views/Theme/`)
- `Views/Theme/Theme.swift`: port Clipfield's `Theme` enum verbatim in spirit: `panelCornerRadius = 18`, `rowCornerRadius = 10`, `badgeCornerRadius = 8`, `promptCornerRadius = 16`, `accent` (from `SettingsManager.shared.accentTheme`), `accentGradient`, `selectionSpring`, `promptSpring`, `hairline = Color.white.opacity(0.12)`, `rowHover = Color.primary.opacity(0.06)`, `chipInactive = Color.primary.opacity(0.07)`, `scrim = Color.black.opacity(0.28)`, `selectionGlow`, plus `Color(hexString:)`. Add a `static func kindTint(_ rawKind: String) -> Color` keyed by the ContentKind raw values (`text` gray, `richText` indigo, `link` blue, `image` purple, `file` gray, `color` pink, `email` green, `phone` teal, `code` orange) - keyed by String so it compiles before the `ContentKind` enum lands.
- `Views/Theme/Appearance.swift`: `AccentTheme` (system, blue, purple, indigo, pink, red, orange, green, teal -> `Color`), `AppColorScheme` (system/light/dark -> `ColorScheme?`). Both `String`-raw `Codable CaseIterable` with `label`.
- `Views/Theme/FontScale.swift`: `enum KlipFontRole { case sidebarTitle, sidebar, sectionHeader, chip, rowTitle, rowTitleMono, rowSubtitle, caption, preview, previewMono, badge }` with base sizes (15, 13, 10, 11, 13, 12.5, 11, 10, 13, 12.5, 10) and a `Font.klip(_ role:)` that multiplies by `SettingsManager.shared.listFontScale` (list roles) or `previewFontScale` (preview roles). Also `CGFloat.klipScaled(_ base: CGFloat, preview: Bool = false)` for frames/padding that must scale with text (row height, badge size). Phase 2 and 3H apply these; you do not sweep existing views.
