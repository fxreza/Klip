# Task 4B — Refute-review of iCloud Drive sync (Phase 4A)

Reviewer stance: try to break it. Every scenario below was either run for real (two `ClipboardStore`s + a fake cloud root, or a live kill‑9 against the actual push path) or traced precisely against the code, per the brief. Nothing in this worktree was edited; this file is the only artifact produced.

## Method

- **Baseline**: `scripts/run_tests.sh` — **215/215 passed** (includes the existing `SyncMergeTests` and `CloudDriveSyncTests` suites, unmodified).
- **Live probe harness**: a standalone driver (`Probe.swift`, built outside this worktree in the scratchpad) compiled together with the actual app sources plus `Tests/CloudDriveSyncTests.swift` / `Tests/SyncMergeTests.swift` / `Tests/ClipboardStoreTests.swift` for their two‑store harness (`Instance`, `withTwoMacs`, `text(...)`), reusing the project's own `KLIP_DATA_DIR` / cloud‑root injection pattern. **14/14 probe scenarios ran and reported clean** — two of them exist specifically to *demonstrate* a real gap (noted below), so "ran clean" means "reproduced the expected/observed behavior," not "found nothing."
- **Kill‑9 durability test**: a second standalone driver (`PushLoop.swift`) that constructs a real `ClipboardStore` + `CloudDriveSync` against temp `KLIP_DATA_DIR`/cloud‑root dirs and loops `pushSynchronously()` on a ~6.5 MB history; the process was `kill -9`'d at essentially random points during steady‑state pushing across **25 trials**, and every resulting `history.json`/`folders.json`/`tombstones.json` was validated as parseable JSON afterward (0/25 corrupt).
- **Code trace** for the two scenarios that real timing can't reliably force (a genuine cross-Mac clock race — approximated instead with two ordered wall‑clock edits) and for privacy/network claims (grep for network APIs).
- No file in this worktree was written except this report. The real `~/Library/Mobile Documents/com~apple~CloudDocs` was never touched — every experiment used temp `KLIP_CLOUD_ROOT`/`KLIP_DATA_DIR` directories.

| 3 | Lock on A vs. delete on B, both before either pulls | **FAIL** | Real test: item synced to both. A locks it (`toggleLock`, bumps `updatedAt`). 50 ms later B deletes it (`delete`, writes a tombstone with `deletedAt` > the lock's `updatedAt`). Both push before either pulls, then both pull: **the item is gone on both A and B**, despite being locked. `Services/SyncMerge.swift`'s tombstone rule (`if let tomb = itemTombstones[id], tomb.deletedAt > winner.updatedAt { continue }`) has no `isLocked` check at all — it only compares timestamps. This directly contradicts the invariant stated twice in the code itself: `Services/ClipboardStore.swift:281` "A locked item can never be deleted or evicted" and `Models/ClipboardItem.swift:37` "Lock state — a locked item can never be deleted or evicted." Locally that invariant is enforced (`delete()` guards `!isLocked`); across the sync boundary it is not. When the lock is the *later* edit instead, the item survives — confirming it's pure recency, not lock-awareness. | **High** | `SyncMerge.merge`'s tombstone check should also require that no surviving version of the record has `isLocked == true` before a tombstone deletes it (an explicit "unlock, then delete" requirement to actually remove a locked clip via sync, matching the local invariant). At minimum this needs to be an explicit, documented product decision rather than an accidental byproduct of "newest wins." |
| 10 | iCloud unavailable at launch, and mid‑session | **FAIL** (adjacent to what the scenario asked) | `startIfEnabled()`/`syncNow()` (what a real launch and the "Sync Now" button use) correctly gate on `isAvailable` and no‑op with no crash, no directory creation, no retry storm. **But** the raw entry points `pushSynchronously()`/`pullSynchronously()` — which `AppDelegate.swift:126` calls directly and unconditionally from `applicationWillTerminate` whenever `isActive` is true — call `ensureCloudDirectories()` first, which unconditionally does `createDirectory(withIntermediateDirectories: true)` with no `isAvailable` check. Real test: constructed `CloudDriveSync` with a `cloudRoot` pointing at a path that does not exist (`isAvailable == false`); calling `pushSynchronously()` directly **silently created the entire `Klip/` folder tree** and afterward `isAvailable` reports `true`. Since `isRunning`/`isActive` is sticky (nothing flips it back to `false` if iCloud Drive becomes unavailable mid‑session — a poll/push/pull that hits `guard isAvailable else { return false }` just silently no-ops, it doesn't call `stop()`), the quit‑time flush in `AppDelegate` can hit exactly this path: iCloud Drive toggled off (or the container temporarily unmounted) while the app was running with sync already started, then quitting the app recreates a `Klip/` folder at a path that was supposed to be treated as unavailable. | **Medium‑High** | Add the same `isAvailable` guard to `pushSynchronously()`/`pullSynchronously()` that `syncNow()` already has, so `ensureCloudDirectories()` is never reached when the cloud root isn't really there. ## Fix-before-release list

1. **#3 — Locked item can be deleted by a remote tombstone.** A lock set on one Mac provides no protection at all against a delete that happened later (in wall-clock terms) on another Mac before either side pulled. This directly contradicts the "a locked item can never be deleted" invariant enforced locally. Recommend `SyncMerge` refuse to let a tombstone delete a record where any surviving version has `isLocked == true`, requiring an explicit unlock-then-delete round trip across devices.
2. **#10 — `pushSynchronously()`/`pullSynchronously()` bypass the `isAvailable` gate.** Unlike `syncNow()`, these two entry points call `ensureCloudDirectories()` unconditionally, which will silently create the `Klip/` folder tree even when iCloud Drive is (or has become) unavailable. This is reachable in production via `AppDelegate.applicationWillTerminate`, which calls `pushSynchronously()` directly, gated only on the sticky `isActive` flag rather than a live `isAvailable` check. Recommend adding the same guard `syncNow()` already has.

Both are real, reproduced findings — not speculative — with a minimal repro in the probe harness described above. Everything else in the 15 scenarios held up under a real two-store run, a live kill‑9 stress test, or a precise code trace; scenario #4's flag loss and #7's unenforced schema-version field are working as currently designed and are noted as product/documentation decisions rather than defects.
